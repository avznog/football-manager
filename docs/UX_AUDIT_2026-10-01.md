# UX audit — `dev.7orteils.bgonzva.fr`

**Date** 2026-10-01 · **Build** `main` at `646b830` (`v1.0.0-beta.6`), preview deployment
**Re-checked against** `b5a6ddb` (PR #114, decision 123), which merged while the audit was running.
Nothing in this report is fixed there; see D2 for what it does and does not change. One later commit,
`c0bfab6` (#119), gives `/connexion`, `/rejoindre` and `app/not-found.tsx` a side gutter that
previously computed to zero — so any gutter measurement below taken on those three screens predates
the fix. No finding in this report rests on one.
**Scope** 52 defects · 11 scope questions · 8 absences · 24 things that are right · 13 stated limits
**Method** Eight parallel audits on the live deployment, 390×844 and 320 px, light and dark,
Chromium and WebKit, as coach (`karim`) and as player (`hugo`). Screens were looked at, not just
asserted about. Writes were made on the preview database only, on data the auditors created
themselves; four seeded states were declared observe-only and were not touched.

**How to read this.** Findings are split three ways, because the fix is a different kind of decision
in each case and mixing them makes a product question look like a bug:

- **DEFECT** — the app does something wrong, or a screen states something untrue. Not a judgement
  call. Fix it.
- **SCOPE** — the app does what it was built to do, and what it was built to do is arguably the wrong
  thing. The owner's call, not a developer's.
- **ABSENCE** — a thing that does not exist. A roadmap item, not a bug.

Within each, ordered by how much harm it does. Every finding names what was observed, why it matters,
and where to change it. A **What is good** section follows, because several things here are better
than commercial equivalents and should not be refactored away by accident. A **Not verified** section
states plainly what this audit could not establish.

## DEFECTS

### D1 — « Tout le monde est là » destroys the pointage on the next save *(data loss)*

The documented happy path of training attendance silently throws away the coach's work.

Reproduced on a throwaway session, 13 players at « — », in **both Chromium and WebKit** and on **both
call sites** (the session page and the inline card on `/entrainements`):

1. Tap « Tout le monde est là ». The card correctly says **« 13 présents sur 13 pointés. »** The
   database now holds 13 présent rows.
2. **All 13 rows below still show « — » selected.** One card, two contradictory statements, six
   inches apart.
3. Do what the code comment tells the coach to do (`attendance-list.tsx:96` — *« one tap for the
   common case, then flip the two who are missing »*): set two players to « Absent », save.
4. **« 0 présent sur 2 pointés. »** Eleven players who were marked présent are wiped back to
   *non pointé*. The player sees it too: Hugo's view of that session reads « 0 présent sur 2
   pointés » for an evening 13 people trained at.

**Cause.** The radios are uncontrolled — `defaultChecked={mark === option.value}`,
`attendance-list.tsx:147` — inside a Server Component. `markEveryonePresent`
(`lib/training/actions.ts:273`) writes and calls `revalidatePath`, but React reconciles the
re-rendered tree onto the *same keys* and **does not reset uncontrolled inputs**, so the DOM keeps
`unset`. The next submit posts `presence:<id>=unset` for all eleven untouched players, and
`markTrainingAttendance` `DELETE`s their rows (`actions.ts:239-248`) — it cannot distinguish "the
coach cleared this" from "the DOM is stale".

**Why it ranks first.** It corrupts the season's attendance rate, which `/stats` is built on; it
happens on the one path the feature was designed around; and the first tap *appears to work*, so the
coach has no reason to check. This is the failure family decisions 099/120 were written to kill,
one step worse — here the write succeeds and is then undone.

**Fix.** Make the shortcut a second `<button formAction={markEveryonePresent}>` **inside the single
form** (`attendance-list.tsx:97-103`), so there is one form, one submit model, and no way to hold
stale radio state when the shortcut fires. The smaller stopgap is to key the form on the marks so
React discards the stale inputs:

```tsx
const markKey = [...marks].map(([id, p]) => `${id}:${p}`).sort().join("|");
<form key={markKey} action={markTrainingAttendance}>
```

Add a test for the exact four-step sequence above — nothing in the suite walks it today.

### D2 — Nothing anywhere in the app acknowledges a tap *(this is the "feels dead on iPhone" complaint)*

The owner's « deux secondes avant que quelque chose se passe » is **reproduced literally**, and the
cause is not speed.

Instrumented with a `MutationObserver` on `document.body` started at `pointerdown`, recording the
first mutation of any kind, then polling until `main` holds new content. CDP network + CPU throttling.

| | first DOM change after tap | new screen content | gap |
|---|---|---|---|
| Fast 4G — Équipe | 232 / 182 / 145 ms | 237 / 187 / 147 ms | **5 / 5 / 2 ms** |
| Fast 4G — Stats | 491 / 381 / 167 ms | 496 / 387 / 171 ms | **5 / 6 / 4 ms** |
| Fast 4G — Moi | 348 / 187 / 169 ms | 349 / 189 / 170 ms | **1 / 2 / 1 ms** |
| Slow 4G — Équipe | 1109 / 563 / 505 ms | 1120 / 574 / 514 ms | 11 / 11 / 9 ms |
| Slow 4G — Stats | 722 / 707 / 582 ms | 734 / 719 / 595 ms | 12 / 12 / 13 ms |
| Slow 4G — Moi | **3138** / 471 / 472 ms | 3147 / 473 / 474 ms | 9 / 2 / 2 ms |
| Slow 4G — cold `/calendrier` | | | **1780 ms** |

**The two columns are the same number in all eighteen samples.** The first thing that changes on
screen after a tap *is* the arrival of the new screen. No pressed state, no spinner, no skeleton, not
one attribute flip in between, at any network speed.

This predicts that **making navigation faster would not fix the complaint** — which is why the
`iad1`→`lhr1` region pin (decision 111), which genuinely worked, did not help. TTFB is **3–27 ms**
across all twelve routes. The server is not the problem. The silence is.

**Systemic cause: « survivors, not coverage. »** Tailwind v4's preflight zeroes
`-webkit-tap-highlight-color` globally — verified on every control in both engines and both themes,
all `rgba(0,0,0,0)`. The app therefore opted out of the one acknowledgement iOS gives for free, on
every control, and only put something back where a developer happened to use the shared
`components/ui` button (which does ship `active:scale-95`). For the login button I walked every
`cssRules` in every same-origin stylesheet, stripped `:active`/`:hover` from each selector and tested
`matches()`: **zero rules target its pressed state at all** — not overridden, absent. Lane C ran the
same enumeration against the calendar rows and found the app's CSS contains **no `:active` rule
outside a `pointer-events` utility block**.

Confirmed silent: calendar rows (538 ms of nothing per tap, on the most-tapped surface after the
chips), the `/stats` filter and sort chips (`filters.tsx:70`, `:152` — `hover:` and
`transition-colors`, no `active:`), both attendance save buttons, the match-hub cards, the form
submits, the composition pitch.

**Fix.** One shared token, applied everywhere, rather than per-screen patches. The rest of the surfaces
above each need the same utility. The calendar rows carry `hover:bg-surface-2`, which on iOS fires only
as sticky post-tap pseudo-hover — i.e. on a page the user has already left — so `active:` is the
missing half, not a new idea.

**Every row of the table above still reproduces on current `main`.** PR #114 merged as `b5a6ddb`
(decision 123) while this audit was running, and what it ships is **one hand-written tap
acknowledgement on the bottom nav** — a hairline fill. The Tailwind v4 preflight point is recorded in
its source comments at `components/nav/bottom-nav.tsx`, which is the file to cite. So the count after it
is **two acknowledged surfaces, not an acknowledged app**, and the arithmetic of this finding is
unchanged.

*An earlier draft of this section carried a caveat saying the `/stats` row was taken before #114 adds a
`<Suspense>` boundary and a skeleton there, so it would not reproduce afterwards. **That is wrong and
is struck.*** The boundary and the skeleton were withdrawn from #114 before it merged —
`app/(app)/stats/page.tsx` is byte-identical to `main` — and the reason they came out is a finding of
the same class as this one, so it belongs here rather than only in that branch's notes:

> A streaming boundary puts the **fallback** in the HTML and swaps the real content in with an inline
> `$RC(...)` script. With JavaScript off the reader is stuck on the skeleton while the content sits
> hidden in the same document — and two of this project's decisions rest on the `/stats` chips working
> with JS off (G23 records that they do). Worse, **the boundary only engages when the query outruns the
> shell flush**, so the fast case keeps the no-JavaScript path and the slow case — which is the whole
> case on a phone at a pitch — loses it. The normal case would have been the broken one, which is worse
> than a uniform limitation, because a uniform limitation is a trade-off somebody can accept. Two more
> defects came out with it: the skeleton promised three cards where a new team's honest answer is often
> zero (the failure family of G1), and the fresh-bootstrap reader would have met three pulsing outlines
> before « Pas encore de statistiques ».

The thing to lead with when fixing this is the CSS enumeration: **no `:active` rule exists anywhere in
the served stylesheet outside a `pointer-events` utility block.** That is one line, it is not a matter
of interpretation, and it is the whole finding.

### D3 — The match sheet saves 6 or 8 starters with no error, and silently empties composition slots

The sheet accepts any number of starters. Measured on Étoile du Parc: an 8th starter selected → badge
still read « 7 / 7 titulaires » → submit 146 ms → redirect to `…/feuille?enregistre=1` with « Feuille
enregistrée. » → after reload the page reads « **8 / 7 titulaires · 8 titulaires · 3 remplaçants** ».
Same with 6 → « 6 / 7 titulaires ». `[role=alert]` was empty at every step. `setMatchSquadSchema` in
`lib/composition/validation.ts` has no `starters === 7` rule.

The second half is worse: setting an already-placed starter to « Hors feuille » **removed him from
both saved compositions**, and the only message was « Feuille enregistrée. » The loss surfaced on the
compositions screen afterwards. `lib/composition/actions.ts` already owns the sentence pattern for
this class of refusal (« Un joueur déjà entré en jeu… »); it should name the slots a role change is
about to empty before emptying them. This is the same family as D1 — a save that reports success
while deleting something the user did not ask to delete.

### D4 — Losing signal mid-pointage discards the whole list, and offers a « Réessayer » that cannot work

With the context offline, marking a player and saving replaces the entire page with the generic crash
boundary after ~5 s. The form, the thirteen rows and every mark in them are gone; back online, the
mark was not saved. « Réessayer » re-renders the segment, it does not resubmit.

This is the exact scenario the component's own doc comment is written for — *« this gets filled in
standing on the touchline »*, *« a dropped connection costs one retry instead of thirteen »*. The
one-submit design does mean one retry, but **there is nothing to retry from**: the coach must redo
thirteen rows on the connection that just failed. Game mode has an outbox for precisely this; the
pointage has nothing.

**Fix.** (a) Do not let a failed submit take the screen: wrap the list in a Client Component using
`useActionState` and render `role="alert"` « Les présences n'ont pas été enregistrées. Réessaie. »
**above the list, with the marks intact**. (b) The marks are a small, idempotent, last-write-wins
payload keyed on `(trainingId, teamMemberId)` — the easiest thing in the app to queue. Persist the
pending `FormData` and flush on reconnect, as game mode already does. At minimum, (a).

### D5 — « Fin du match » only ends the period, and ending a period is one unconfirmed tap

On the last period `periodEndLabelFr` returns « Fin du match » for a `PERIOD_END`
(`lib/match/presenter.ts:~1010`). One tap recorded « 46' Fin de période », froze the clock, and the bar
then offered ACTION 239×56 beside a differently-named « Sifflet » 119×56 — which is what actually ends
the match. `game-mode.tsx:430-432` opens a `ConfirmSheet` only for `FINAL_WHISTLE`; `PERIOD_END` emits
immediately. So a thumb landing beside ACTION ends the half and freezes the clock with no guard, while
a far less consequential row-level « Annuler » gets a full confirm sheet. This produced the auditor's
own first half ending at 6' with a 24-minute hole. The naming then tells the coach he has already done
the thing he still has to do. Recoverable only by appending a `VOID`.

**Fix.** Name the button after the period on every period (« Fin de la 2e »), and give `PERIOD_END` the
same confirm as the whistle — or at minimum an undo in the acknowledgement.

### D6 — In retro entry, the field that names the scorer is created 487 px below the button that creates it

`/saisie` at 390×844, scroll 0, document 2069 px. « + But pour nous » sits at y=518 inside the
« Score » card. Tapping it increments the visible score to « 1 – 0 » **and appends the goal's row to
the « Actions du match » card at y=1331** — 487 px below the fold. The auditor did not notice, saved,
and the match recorded « 30' But — buteur non renseigné ». The defect produced, unprompted, exactly
the missing-scorer data that `/stats` has to apologise for in G1.

The only feedback at the thumb is the score ticking up, which reads as completion, and « Un appui par
but » in the Score card actively confirms the wrong mental model. The scorer, the assist and the
minute are all off-screen in a card the coach has no reason to suspect changed.

**Fix.** Cheapest option reuses working code: have the Score card's buttons open the same bottom sheet
correction mode already uses (« Ajouter une action » — modal, complete, and good). Otherwise put the
row inside the Score card, or scroll and flash it into view.

### D7 — Eleven rating cards, both controls below the fold, and the progress is lost if you leave

Two defects that compound each other.

**The fold.** At `scrollY: 0` with `docH: 1097`: the 0–10 pad's last row ends at y=684, « Précédent » /
« Passer sans noter » sit at y=849 and « Enregistrer mes notes » at y=937. The fixed tab bar takes the
last 56 px, so the usable fold is ~788 — **253 px of overflow.** Decision 102 deliberately makes
advancing a second deliberate tap; this layout makes it tap + scroll + tap, eleven times over. Game
mode already solves it with `sticky bottom-0`.

**The loss.** Rated two players, navigated to `/calendrier`, came back: « 0 / 11 notés », card reset to
the first player, nothing persisted — no guard on leave. Eleven cards is a multi-minute task on a phone
that rings. Note the asymmetry: **game mode protects the coach's taps with an IndexedDB outbox; the
rating sheet's 23 taps have nothing.** Credit where due — the app does warn passively, rendering
« 11 notes choisies, pas encore envoyées. » in `text-warning` with `aria-live` — but it is text only,
and it cannot survive a navigation. Same family as D4.

Compounding both: the sheet's order is unexplained and non-monotonic (n° 1, 2, 3, 4, 6, 7, 9, **8**,
10, 11, 12 against « joueur N sur 11 »), with Précédent/Suivant as the only navigation — so revisiting
one player means stepping through the others.

### D8 — A coach can demote himself out of the app with one tap, and the control looks like plain text

On Karim's own profile — badged « coach » « joueur » « **c'est toi** » — the Fiche card reads
« Rôle · Coach · **Retirer coach** », a live submit button. `app/(app)/joueur/[id]/page.tsx:172`,
guarded only by `canAppointCoach && !profile.isLastCoach`. The removal card twenty lines below
(`:230`) *does* carry `&& !isSelf`.

AS Dimanche has two coaches, so the last-coach guard does not fire. **One tap and Karim demotes
himself out of the entire coach interface, with no confirmation and no way back without the other
coach.** The page already knows it is looking at `isSelf` and already uses that fact elsewhere.

Compounding it: `components/ui/button.tsx` `ghost` is `text-ink hover:bg-surface-2
active:bg-surface-2` — no border, no background. At 390 px « Retirer coach » is an indented plain
word. **The self-demotion control does not look like a control**, which is what turns a footgun into
a likely accident.

**Fix.** Add `&& !isSelf` at `:172`, matching `:230`. If self-demotion must remain possible it belongs
on `/moi` with its own description. Separately, give `ghost` a resting affordance.

### D9 — The chronologically next match is hidden from « À venir » and filed under « Déjà passé »

`/calendrier` shows « À venir » containing exactly **one** row (04/10). « Déjà passé », under the
heading « Le plus récent en premier. », **opens with a match dated 18/10/2026** — seventeen days in
the future — above a row from 27/09.

Server clock verified against the HTTP `Date` header: today really is 2026-10-01. **Not a clock bug
and not a sort bug.** `matches.status = 'finished'` on that row, so `isFinishedEvent` → `isPast`
returns true whatever the date says (`lib/calendar/timeline.ts`), `splitTimeline` puts it in `past`,
and `past` is sorted by `startsAt` **descending** — so a future kick-off sorts to the top. This is
**decision 121 behaving exactly as written**: a match dated next Sunday can be declared over, and 121
deliberately added `isFinishedEvent` so the row would not sit under « À venir ».

The mechanism is designed. What the screen now says is not:

1. **A player looking for his next match is told there isn't one.** He scans « À venir », sees one
   fixture, and concludes the season ends next Sunday. The calendar is the home screen.
2. **« Le plus récent en premier » is false as written.** The first row under it is the one thing in
   the list that has not happened. Decision 087's own rule — a heading is a claim about every row
   under it — fails here.
3. **It is indistinguishable from a genuinely un-typed-up past match.** « À AS Coteaux, 18/10, Rien
   saisi » (not yet kicked off, declared over) and « À FC des Deux-Ponts, 20/09, Rien saisi » (really
   played, nobody recorded it) get the same badge, same styling, same section.
4. **Nobody can answer availability for it.** `/match/<id>` renders no availability control at all,
   and the calendar row links to `/recap`. A match 17 days away is unanswerable.

**Fix — do not undo 121, the mechanism is right. Make the row say what it is.**
- `event-parts.tsx`, `PastMatchResult`: when `score === null` **and** `startsAt > now`, render
  « Déclaré terminé » rather than « Rien saisi ». Pass the `now` that `page.tsx` already has.
- Make the section description conditional: when `past` holds a future-dated event, « Le plus récent
  en premier. » is wrong. Put it next to `pastSectionTitleFr` in `timeline.ts` so it is unit-testable
  the same way.
- Better: a future-dated finished match deserves its own one-row section between the pinned card and
  « À venir ». It is neither.
- Separately, `finishMatch` should **confirm and name the date** when the kick-off is in the future
  (« Ce match est prévu le 18/10/2026, dans 17 jours. Le déclarer terminé ? »). 121 chose no
  chronology gate on purpose; a confirmation is not a gate.

### D10 — A match « terminé » 17 days in the future loses its entire preparation workflow

AS Coteaux, 18/10/2026, `status='finished'`: the hub says « Le match est joué » and « Ce match a été
joué sans le téléphone », the compositions screen says « Le match est joué et personne n'a été retenu
sur la feuille : il n'y a rien à composer », and **there is no « Ta réponse » card and no
« Disponibilités » card at all**. The only escape is a ghost link at the bottom, « Terminé par
erreur ? Rouvrir le match ». This is the write-side twin of D9, which is the same row lying on the
calendar. `page.tsx` already computes `played = kickoff <= now`; when `status === "finished" &&
!played` it should say so at the top and keep the availability cards.

**And the symmetric failure, found independently from the other side.** On a match dated three days in
the *past* and already typed up, the « Ta réponse » card is live and says « Tu peux changer d'avis
**jusqu'au coup d'envoi** », offering Dispo / Pas dispo / Peut-être. So the hub shows the availability
poll on exactly the two matches where it is meaningless, and hides it on the one where it is needed.
One condition — availability is open iff the match is neither finished nor kicked off — fixes both
halves, and decision 120 already established that this kind of rule belongs in one place asked by all
its callers (G4).

### D11 — A match with an empty event log says it was typed up, and offers a summary of nothing

FC des Deux-Ponts has no events. Both the hub and the compositions screen print « **Saisi sans
composition** — Ce match a été saisi après coup, sans composition : les temps de jeu viennent de la
saisie et non d'un placement sur le terrain. » over a green « 7 / 7 titulaires » badge. There are no
minutes and there was no saisie. The header shows no score and says nothing about the absence — the
calendar manages « Rien saisi » for the same match; the hub stays silent. And the hub's first filled
primary is « Voir le résumé » at y=756, *above* « Saisir le match » at y=974, so the unrecorded match
invites you to read a summary of nothing before recording it.

`compositionsScreenFr` (`lib/composition/plan.ts:437-444`) takes no `recorded` argument, while the hub
already computes `score !== null` at `page.tsx:98`. Pass it, and give the retro branch a second
sentence for « rien n'a encore été saisi ».

### D12 — « 11 présents sur 14 pointés » for a squad of 13, and two latent variants of the same bug

`/calendrier` shows « 11 présents sur **14** pointés » (05/09) and « 0 présent sur **13** pointés »
(19/09), while `/equipe` says « **13** joueurs ».

**The 14 is historically true.** `getTeamAttendanceCounts` (`lib/training/queries.ts:128-148`) counts
every `training_attendance` row with no filter on `team_members.left_at`; Rayan left ~20 days ago, so
the 05/09 session was pointed with 14 in the squad. The record is faithful — but the screen gives the
reader no way to reach that conclusion, and the only available inferences are "the app miscounts" or
"we had 14 players", neither of which is right.

**The same missing filter, with a worse consequence, is latent in two more places.**
`getTeamMatchAnswers` (`lib/match/queries.ts:131-142`) and `getTeamTrainingAnswers`
(`lib/training/queries.ts:76-86`) also lack a `left_at` filter, while `squadSize` in `getCalendar` is
active members only. So `answersLineFr` adds answers from a larger population than it subtracts from,
and `pendingCount`'s `Math.max(0, …)` **hides** the overflow rather than surfacing it. Today's data
does not expose it, but a past event whose answers include a departed player will print a line
summing to **14 with « 0 sans réponse »**, while the match's own page — correctly driven by the squad
list via `tallyAvailability` — says 13.

**Fix.** Name the denominator rather than letting it float: « 11 présents sur 14 joueurs ce soir-là ».
Do **not** filter departed members out of `getTeamAttendanceCounts` — that would delete Rayan from a
night he attended, the invention decision 013 refuses. Then add `isNull(teamMembers.leftAt)` to both
*answer* queries, where there is no history to preserve, and the clamp becomes a belt rather than the
braces.

### D13 — The recap labels every named substitute « entré en jeu », including men who never came on

CS Morvan, both themes: in « Les notes », Fabien #14 and Yanis #10 carry a neutral pill « entré en
jeu »; in « Temps de jeu » on the same screen the same two men read « non entré » with 0 minutes.
Identical pill styling, opposite meaning, one scroll apart. The recap is the artefact players
screenshot and argue over, and it announces playing time that did not happen.

What makes this worth ranking high is that **the fix already exists and landed on the wrong route.**
`recap/_components/ratings-panel.tsx:91-93` reads `player.squadRole === "substitute"`. The helper

exact bug, `progress.test.ts:137` regression-tests it, and `rating-flow.tsx:278-295` already applies
it — on `/notation` and not on `/recap`. Or drop the badge entirely: the minutes table states minutes
exactly, two cards away.

### D14 — The composition editor opens with the pitch behind its own dock: zero slots tappable

Measured identically in Chromium and WebKit, light and dark, at 390 px and at 320 px: pitch top 508,
height 410; sticky dock 568–788. **193–221 px of the pitch is covered and all seven slots have
`bottom > dockTop` — not one slot can be tapped without scrolling first.** On WebKit exactly one disc
is visible. The consequence is not cosmetic: a bench→slot drag aimed at a midfield slot lands on the
dock, which is tested *before* `nearestSlot`, so the drop is read as "return to bench" — « Karim reste
sur le banc. » and nothing placed. It happened twice before scrolling. The read-only card on the hub
renders a ~650 px pitch; the editable one gets about 60. Fix at
`components/composition/composition-editor.tsx:235` — scroll the pitch above the dock on mount, or
collapse the dock to one line while a drag is in flight.

Measured at 390 and 320, identical: « Modifier » 82×44 white, « Supprimer » 94×44 transparent ghost,

### D16 — The coach generates an invite code, and the app never builds the link it tells him to send

The card says « **Génère un code et envoie-le sur WhatsApp** ». After generating, there is a banner
« Code créé : 3E4G-UT7V » and a list row — and **no URL, no copy button, no share control anywhere on
the screen**. Yet `/rejoindre` supports `?code=`, and `app/(auth)/rejoindre/page.tsx:20` literally
calls it "the invite link the coach shares on WhatsApp". The dashed form was verified working:
`/rejoindre?code=3E4G-UT7V` pre-fills and resolves.

**This is the product's entry path.** The coach must type nine characters into WhatsApp with no
destination, and the invitee receives a code with nothing to do with it. The one screen that could
produce the link knows the code and does not.

**Fix.** `invite-manager.tsx` — render the absolute `/rejoindre?code=…` URL beside each active code
with a copy control, and `navigator.share` where available.

### D17 — `/rejoindre` never names the team or the role, even with a resolvable code in hand

With `?code=…` the screen says only « Rejoindre une équipe » / « Ton coach t'a envoyé un code
d'invitation ». Nothing says **AS Dimanche**, and nothing says whether the code makes you a joueur or
a coach — though the coach chose that in a selector and the server can resolve both from the code
before rendering.

A stranger arriving from a WhatsApp message is asked to create a password and commit to an
organisation that is never named.

**Fix.** Resolve the code server-side when present: « Rejoindre **AS Dimanche** » with « Ce code te
fait entrer comme **joueur** ». Keep the current wording as the no-code fallback.

### D18 — After a rejected save, every `<select>` on the retro form visibly blanks while the data is still there

Before the rejected save: scorer « 6. Léo », assist « 4. Thomas », minute « 12 », « Sort… 9. Julien ».

## SCOPE — the owner's call, not a developer's

### S1 — `/stats` is 6658 px (7.9 screens) and opens on its own footnotes

| route | px | screens |
|---|---|---|
| `/stats` | **6658** | **7.9** |
| `/equipe` | 3524 | 4.2 |
| `/match/[id]` | 2910 | 3.4 |
| `/stats/equipe-type` | 1965 | 2.3 |
| `/calendrier` | 1567 | 1.9 |
| `/moi` | 877 | 1.0 |

`/stats` is nearly twice the next-longest screen with no internal navigation — no sticky section
switcher, no anchors, no collapse. Reaching « Présence aux entraînements » is roughly seven flicks.

And **on the first screen the caveats outrank the statistics**: after the real figures, roughly
410 px — about half of what remains above the fold — goes to three paragraphs explaining what is
*missing*. The page opens on its own footnotes, and « L'équipe type », the most interesting thing on
it, is clipped at the bottom edge.

**The paragraphs are the best writing in the app and must not be deleted** (see G1). The problem is
rank, not existence. Collapse them behind one line that states the reconciliation — « 8 terminés,
dont 2 sans évènement saisi — 6 comptés » — with the detail in a disclosure. That also fixes the
« 8 matchs terminés » / « 6 matchs comptés » contradiction, which the reader currently meets about
300 px before its explanation.

### S2 — « La meilleure équipe » seats five players who scored nothing, and the estimated figures are not marked as estimated

On `/stats/equipe-type`, only Julien (5 buts) and Karim (3 buts) have a non-zero count. The other five
read « 0 but sur 360′ », « 0 but sur 324′ », « 0 but sur 36′ ».

**I checked whether the rates were simply wrong, and they are not.** Brice shows « 0,20/h » beside
« 0 but sur 36′ », which looks like a contradiction, but the page explains it: « Les buts par heure
sont ramenés vers la moyenne de l'équipe, à hauteur de 1,6 heure de jeu. » It is a shrinkage
estimator with a 1.6-hour prior, and « Total des sept · 2,01/h » is exactly the sum of the seven
displayed rates. The arithmetic is right and documented.

Two consequences are worth the owner's attention anyway:

1. **The estimate is not marked as one at the point of use.** « 0,20/h » sits directly above « 0 but
   sur 36′ » with nothing indicating it is shrunk toward the mean; the explanation is at the bottom of
   the page. A reader who does not scroll sees a figure that contradicts its own caption. Marking it
   (« ~0,20/h », or « estimé ») costs one character and removes the apparent contradiction.
2. **Shrinkage with a 1.6-hour prior ranks thin evidence above genuine zeroes.** Brice's 36 minutes
   pull him toward the team mean and he lands *above* three players with the same 0 goals over
   324–360 minutes. That is correct Bayesian behaviour and counterintuitive football, and it puts a
   player who played 36 minutes in the équipe type ahead of players who played ten times as long.

With a 13-player squad and one metric, the pool may simply be too thin to rank. That is a product
judgement. Note that `/stats` caveats this kind of thing beautifully and **this screen caveats the
thinness not at all** — the inconsistency is the part I would act on.

Tailwind's scale is 12/14/16/18/20/24/30. **9, 10, 11 and 15 px are arbitrary values** that have

**Nothing on screen is untrue and no user will report this.** It is the drift that makes an app feel
assembled rather than designed, and it is cheapest to fix at eleven sizes rather than twenty.
Proposed scale: 11 · 12 · 14 · 16 · 20 · 30, declared beside the colour tokens in `app/globals.css`.

### S4 — The loudest thing on the calendar is « Nouveau match », not the next event

For the coach, the only filled-accent element above the fold is « Nouveau match ». The pinned card's
`h2` is « **Entraînement** » at 24 px — repeating the « Entraînement » badge 130 px above it and the

Travail sur les sorties de balle ») is 14 px grey beneath it.

The screen's stated purpose (`next-event-card.tsx`: *a player opens the app to answer one question —
am I there on Sunday?*) is delivered, but for a coach the hierarchy says the first job is to create a
match. That is a weekly action; reading the next event is an every-visit one. The player's view is
cleaner and reads much better.

**Fix.** For a training, make the card's `h2` the session's theme when there is one — « Sorties de

match » to `secondary`, or move both buttons below the pinned card.

### S5 — The pointage is last on the page on the evening it is the only thing that matters

With the window open, the first player row sits at **y = 1529 px** and « Enregistrer les présences »
at **y = 2464 px** of a 2597 px page. The coach scrolls roughly two full screens — past « Ta

500 px to scroll past.

### S6 — « — » is the loudest thing in every attendance row

An unpointée session renders as a column of 13 solid filled blocks, because `peer-checked:bg-ink-muted`
paints "not judged yet" with the same weight as `bg-success` and `bg-danger` paint the two real

unselected labels a visible resting affordance.

### S7 — A cancelled session is expressed by thirteen taps and a theme field

The 19/09 session was cancelled on the spot. The app has no way to say that, so the coach wrote
« Terrain impraticable, séance annulée sur place » into a field the form labels **« Au programme »**

Worse, **on the list the explanation is the part that gets truncated**: « Stade municipal · Terrain

### S8 — `/composition` and `/feuille` 404 for a player, while `/jeu` shows him the same lineup read-only

The permission doors are excellent (G13) with one arguable inconsistency. `/match/[id]/composition` and
`/match/[id]/feuille` return 404 to a player — but `/match/[id]/jeu` returns **200** with « Tu suis le
match en direct. Seul l'opérateur du match peut enregistrer les actions. »

The lineup a player is *in* is information he legitimately wants, the app already shows it to him
through another door, and the refusal is therefore not protecting anything. **The best refusal in the
product is not a 404 at all** — `/jeu` grants read, names who may write, and says so. Consider that
shape for those two rather than a 404.

Related, smaller: two 404 *shapes* exist for different causes. `/match/[id]/direct` (not a route —
live mode is `/match/[id]/jeu`) falls through to the **root** not-found, outside the app shell with no
tab bar, while a coach-only route gets the in-app one inside the shell. Defensible — "no such route"
is not "not for you" — but a user cannot tell which he hit.

### S9 — The read-only positions card states the same fact three times

Card description, then 11 disabled chips plus a full legend, then « Poste principal : Gardien de but. »
— roughly 470 px of pitch plus 11 `disabled` buttons a player can tap with no response. Also: the

### S10 — On an upcoming match, the hub's visual primary is the action that ends it

Étoile du Parc, three days away, 2930 px of hub. « Compositions » is a 116×44 white outline link and
« Feuille de match » a 132×44 *transparent* text link, both at y=2249. The only two filled accent
`rgb(11,95,164)` full-width buttons on the page are **« Saisir le match » (324×48, y=2535)** and
**« Ouvrir le mode match » (y=2793)** — and the « Terminer le match » card comes *before* « Mode
match » in the page order.

Three days out, the coach's next action is the sheet and the composition. On a brand-new match the hub
gets this right — « Feuille de match » *is* the accent primary — so what happens is specifically that
**as soon as a sheet exists the composition card drops to secondary while the finish card stays
primary.** Mechanically: `app/(app)/match/[id]/_components/finish-match-card.tsx:48-62`, where the
`beforeKickoff` branch today differs from the played branch only by one extra sentence, and card order
at `page.tsx:98-135`. Filed as scope rather than defect because nothing on the screen is untrue — the
rank is the question, and it is the same question as S4 and S5.

### S11 — A match played in the app can never be deleted, and nobody chose that explicitly

`/match/[id]/modifier` offers « Supprimer » only while the event log is empty (decision 003), and
`deleteMatch` refuses regardless once events exist (`lib/match/actions.ts:146`). Both are invariant 1
working exactly as designed — the log is append-only, so there is no correct way to remove a match that
has one. Verified on three matches created and played during this audit: all three are permanent, and
clearing them needs a `DELETE` against the database.

**The question is not whether the invariant is right.** It is: a match with a typo in its name, a
duplicate created by a mis-tap, a friendly that was abandoned after ten minutes — each of those is
permanent in the calendar for the rest of the season, and the only visible escape is to rename it. Is
that acceptable? Possible answers, cheapest first: rename is enough and this is fine as it is; add a
« masquer » flag that hides a match from the calendar and the statistics without deleting its log; or
allow deletion of a match whose log contains nothing but a kick-off. Nothing here is a defect, and a
developer should not pick one of those three unprompted — which is exactly why it is in this section.

- **A1 — No way to change your own password, anywhere.** `/moi` offers theme, positions, injury,

- **A5 — « parti » is not explained on first use.** Rayan carries the badge in two leaderboards,

## WHAT IS GOOD — do not refactor this away

### G1 — The app refuses to state a number it cannot justify. This is its best property.

On `/stats`: « 1 but sans buteur renseigné : le score de l'équipe est toujours juste, mais la somme
des buts des joueurs est plus basse (c'est prévu — un but peut être saisi sans buteur). » · « 2
matchs terminés sans aucun évènement saisi : ils ne sont comptés nulle part, ni en victoire ni en
défaite. Une saisie rétroactive les ferait apparaître. » · « 1 match en cours est exclu de ces
statistiques : ses minutes bougent encore. Il sera compté après le coup de sifflet final. »

Three different reasons a number might surprise you, each named, each with what to do about it. On
`/stats/equipe-type`, four distinct shrinkage reasons are named rather than one generic excuse, and
the goalkeeper model is spelled out: « un gardien remplacé à la mi-temps garde ses minutes sans
encaisser même si l'équipe a ensuite pris un but. » The attendance section states its own rule: « un
joueur non pointé n'est pas compté comme absent. »

Most production dashboards show 13 goals and 12 scorers and let the user wonder whether the app is
broken. **This is the hardest thing to get right on a statistics screen and it is right.** The only
change wanted is to its rank on the page (S1), never its content.

### G2 — The ratings gate shows different numbers to different people and says why

Karim sees Julien at 9,0; Hugo sees 8,5. Each is told how many matches are masked and the reason:
« tu étais sur la feuille et tu n'as pas encore noté tes coéquipiers. Tes notes débloquent les
leurs. » Clear, actionable, no jargon, and the gate never shows a blank where a number should be —
which would be the worst version of this feature.

### G3 — The availability chips are the best-built control in the app

102 × 44 each, native radios with `peer-checked:bg-*` and a 150 ms `transition-colors`, so the
segment fills **on the tap itself, before any round trip** — real optimistic feedback with no state
management at all. An `aria-live="polite"` region announces « Enregistrement… » with `min-h-5` already
reserved so nothing jumps. `useIsHydrated` keeps a working « Valider ma réponse » submit for a phone
with no JavaScript. Measured: first paint change at **21 ms** in WebKit on the attendance row labels.
This is also the most-tapped control in the app. It is exactly right.

### G4 — Decision 120 holds, verified empirically against all three callers

With the pointage window **shut**: `/entrainements` offers nothing, the session page explains the
rule, « Tout le monde est là » exists nowhere. With it **open**: the inline list appears, the shortcut
writes, and the write persists across a reload. **No control anywhere in the trainings lane does
nothing.** The bug decisions 099/120 were written about is dead. (D1 is a different failure — the
control works and is then undone.)

### G5 — The deletion warning counts, rather than categorises

`trainingDeletionWarningFr` names **both** cascades with counts, and all four branches were seen on
live data: « et avec elle **1 réponse** et **le pointage de 2 joueurs**. C'est définitif. » · « … et
avec elle **le pointage de 13 joueurs**. » · « … et avec elle **9 réponses**. » · and the empty
branch. Correctly absent on a past session. Delete → redirect in 336 ms → a clean 404 on the old URL.
This is a safeguard working as designed.

### G6 — Intention and observation are kept rigorously distinct, including where they touch

An attendance row reads « 1 Hugo / **Annoncé pas dispo** » beside « Présent | Absent | — ». Two
registers in one row, never merged into one sentence. **No screen in the audit counts an availability
answer as an attendance fact.** Decision 090 is genuinely enforced — and D25 is the one place the
distinction is *under*-communicated rather than violated.

TTFB **3–27 ms** across all twelve routes; DCL 147–437 ms; FCP 132–260 ms. `/stats` — one of the two
heaviest queries in the app, aggregating a whole season — serves in under 300 ms. There is no
transatlantic round trip left to find. **Performance is not the complaint**; D2 is.

### G12 — Departed members keep their history, and the screens say so

Rayan appears in two leaderboards with a « parti » badge, is excluded from the current squad table,
keeps his goals and assists in the season totals, and reads `1/1` in attendance because the session
after he left is correctly excluded. One screen does hard arithmetic about a departed member and then
explains the discrepancy out loud: « 11 présents sur 14 pointés. 1 joueur pointé ce soir-là a quitté
l'équipe depuis. » That is the honest accounting, and D12 is a presentation problem on top of a
correct record.

### G13 — The permission model holds at the door. This is the strongest result in the audit.

All eight coach-only routes, opened by URL as a player, return **HTTP 404** and render the identical
in-app not-found inside the app shell: « **404** / Page introuvable / Ce lien ne mène à rien : la page
n'existe pas, ou elle est réservée aux coachs. / Retour au calendrier ».

`/match/nouveau` · `/match/[id]/modifier` · `/match/[id]/feuille` · `/match/[id]/composition` ·
`/match/[id]/composition/nouvelle` · `/match/[id]/saisie` · `/entrainements/nouveau` ·
`/entrainements/[id]/modifier`.

- **No coach control leaks.** On every one of the eight pages the only form controls in the DOM are
  the three theme radios. Nothing disabled-looking, nothing live, nothing that fails on tap.
- **No link to a door he cannot open.** Crawling eight player-reachable screens found **zero** hrefs
  matching `/(nouveau|modifier|feuille|composition|saisie|direct)/`.
- **The refusal is honest** — it names the real reason rather than pretending the URL is malformed —
  and it offers a way out.
- **The inverse was verified by navigation, not only by URL:** everything a player needs is reachable.
  `/match/[id]/recap` 200, `/match/[id]/notation` 200, availability chips on `/entrainements`,
  `/stats` and his own profile fully readable.

This is the part of the app most likely to have been sloppy, and it is not.

### G14 — The preferred-positions editor is the best control in the app

48 × 48 chips; one tap → secondaire, two → principal, three → back. The `aria-label` states the
current state *and* the next one: « Milieu central, poste non souhaité — appuyer pour en faire un poste
secondaire ». Save is disabled until dirty, « Annuler » appears only when dirty, and the status line
reads « Modifications non enregistrées. » / « À jour. » Do not touch it.

### G15 — The roster's `sr-only` positions sentence gives a blind user more than a sighted one

Rows render « @karim · **AG** MC MOC AT AD » with the codes `aria-hidden`, and an `sr-only` sentence
carrying « Poste principal : Ailier gauche · postes secondaires : … ». A genuinely good pattern — the
irony is that it is only half-applied, since AG/MOC/AT are never expanded for a sighted reader on that
screen and bold is the only signal for *principal*.

### G16 — « Effectif » vs « Encadrement » reconciles exactly, and is derived rather than hardcoded

Header « 13 joueurs » = 13 Effectif rows; Encadrement = 1 row, with « **1 coach joue aussi, et
apparaît dans l'effectif.** » — exactly the sentence that prevents the double-count a reader would
otherwise suspect. Nobody missing, nobody counted twice. Both numbers come from `squad.filter(…)`, and
they tracked correctly through 13 → 14 → 13 as a test member joined and left.

### G17 — Both input paths into the composition editor work, and every one announces itself correctly

Tap-then-tap **and** real pointer drag both place and swap, in Chromium and in WebKit (the drag is
drivable headlessly — `mouse.down` plus about sixteen interpolated moves). Every outcome is announced,
precisely and correctly tutoied: « Karim est placé au poste de milieu central. », « Ali remplace
Julien. », « Hugo retourne sur le banc. », « Karim reste sur le banc. » Undo is real, not decorative:
« Tout vider » emptied all seven slots and « Rétablir » restored the saved plan exactly, verified slot
by slot. Geometry is deliberate — disc 48×48, bench cell 64×75 with `touch-pan-x`, tightest slot
centre-to-centre 69 px at 390 and 63 px at 320 (21 px and 15 px of clear space between two discs), and
the dock's bottom edge at 788 sits exactly above the 56 px tab bar. Two controls deep in this screen
are the best in the app; D14 is about where the pitch starts, not about how it works.

### G18 — Blocking validation sits where the decision is made, and nothing broken ever saved

« Il reste un poste à pourvoir. **Personne n'est dans les buts.** » appears in the dock, in red, above
a disabled submit, with no scrolling needed. Likewise « Une composition démarre déjà à la 30ᵉ
minute. » and « Il y a déjà une composition de départ. » Across the whole lane no invalid composition
was ever accepted — which makes D3, where the *sheet* accepts 6 or 8 starters silently, look like one
missing rule rather than a missing habit. Frozen states are equally right: `/composition/nouvelle` on
a played match refuses with the full explanation and a way back, and an applied plan carries
« appliquée » plus « Cette composition a été confirmée pendant le match : elle ne change plus. » and
loses its Modifier/Supprimer entirely. Submit disables while saving everywhere, with `aria-busy="true"`,
« Chargement… » and pointer events off.

### G19 — The brand-new-match empty states are the best copy in the app

« Personne n'est encore retenu — Choisis d'abord tes titulaires et tes remplaçants : seuls eux peuvent
être placés sur le terrain. », with « Remplir la feuille » as the single primary. It names the state,
explains the dependency, and offers exactly one action. The sheet itself is as economical: a four-way
control per row, 76×44 at 390 px and 58×44 at 320, `sr-only` full words, with the declared availability
badge *and* « Blessé » on the very row where the choice is made — **10 taps to build 7 starters and 3
substitutes, which is the theoretical minimum.** The period hint totals correctly and recomputes live:
« 2×30 minutes : 60 minutes de jeu, et la 2ᵉ période va de la 30ᵉ à la 60ᵉ minute. » And across about
60 navigations over the hub, sheet, editor and match forms — including deliberately invalid submits, an
out-of-range minute, and a revisit to a deleted match — there was **no error boundary and no 500
anywhere**, axe reported **0 violations on 20 screens**, vouvoiement **0 hits**, and horizontal
overflow **0 at both 390 and 320 px**, in both engines and both themes.

### G20 — Retroactive entry is the best-written feature in the app, and one sentence on it is the best in the app

« Pas besoin du mode match pour un match joué sans le téléphone. » · « Rien pour l'instant. Un 0 – 0
sans rien à signaler, ça existe. » · « Aucun changement. La composition de départ est vide : sans
titulaire, il n'y a personne à remplacer. » And on the recap:

> « Ce match a été saisi après coup : les actions sans minute précise ont été placées au mieux, donc
> les temps de jeu sont **approximatifs**. Le score et les buts, eux, sont **exacts**. »

That sentence tells the reader precisely which numbers to trust and which not to, in one line, without
apologising. It is the clearest expression anywhere in the product of the property described in G1, and
it should be the model for every caveat the app ever writes.

The validation underneath it matches: « Ce match dure 60 minutes : la minute 999 n'existe pas. », « Il
faut dire qui s'est blessé. » — in `aria-live`, with the save button disabled and **the reason repeated
beside the disabled button as well as on the offending row**, which answers "why can't I save" before
it is asked. D22 is the one case this validator does not cover, which is why it is the only one that
reaches the server.

### G21 — Invariant 1 is not just honoured, it is visible to the user

Correction mode explains itself before acting: « Une correction ne réécrit rien : l'action fautive est
annulée et la bonne est ajoutée. Les deux restent dans le déroulé. » Then it pre-fills the sheet, badges
the voided row « annulé », and afterwards says « Correction enregistrée. Les statistiques de la saison
ont été recalculées. » « Corriger » is offered on facts only, never on a kick-off or a period end. In
game mode the `VOID` confirm reads « L'action reste dans le déroulé, barrée : le journal du match n'est
jamais réécrit. » An append-only log is an architectural decision most products would hide; this one
teaches it, in two sentences, to a footballer.

The rest of the live flow holds equally: **a never-recorded recap never prints « 0 – 0 »** — « ? – ? »,
« rien saisi », « Rien n'a été enregistré » — reproduced from scratch on a fresh match, so it is a rule
and not a seeded special case. Invariant 3 holds: the composition is proposed, never applied. The clock
is continuous (the second half read 30:02, never 00:00), freezes when paused and drops « , en cours »,
and the displayed minute is the minute the event is stamped with (decision 031). The final-whistle sheet
restates the score before freezing (« Score final 2 – 3 contre … ») and the finished screen retitles
its card to « En dehors du terrain » and disables all six buttons. Duplicate starters are impossible.
Arithmetic reconciles exactly on two seeded matches (420 = 7×60 on both), every rating average is
exact, and a voided goal is excluded from both the score and the clean-sheet minutes.

### G22 — The offline queue is genuinely idempotent, and the live flow is fast

Three events queued offline, reconnection, **each landed exactly once**, IndexedDB drained to 0, and the
pending count was exact at every step — invariant 6 verified empirically rather than read. Measured on
the deployed preview: goal tap → score change 63 ms; apply composition 127 ms; the same two while
offline 50 ms / 47 ms; WebKit real touch tap → sheet 62 ms and tap → score 91 ms; final whistle tap →
sheet 33 ms, confirm → closed 70 ms; retro save → recap 677 ms. **Four taps** take "a goal happened" to
"recorded with scorer and assist"; **two taps, with a confirm sheet**, undo a wrong scorer. Game mode is
the one area of this app where the tap feels like a tap — which is the counter-example that proves D2 is
a coverage problem and not a platform limit.

### G23 — Smaller things that are right

No horizontal overflow at **320 px** on any screen any lane tested, including the dense attendance
list — a lot of mobile-first apps fail this. Content clears the tab bar by 15 px at full scroll in all
eight role × theme combinations. Invalid query parameters (`?critere=nonsense`, `?formation=9-9-9`,
`?competition=zzz`) fall back to sensible defaults rather than erroring. The login form posts without
JavaScript (`<form method="POST">`, self-posting), and `/stats/equipe-type` ships a `<noscript>`
submit fallback. `/moi` correctly omits the team switcher for a one-team member rather than showing a
one-option select. The injury disclosure is collapsed by default, which is right for a rare action,
and correctly replaced by « Ta guérison se déclare depuis ta fiche » when already injured. Logout is
findable — only its colour is wrong.

### G24 — The two `<nav>` elements are **not** a duplicate-landmark defect

Both carry `aria-label="Navigation principale"`, which looks alarming in a DOM dump. The first is a
desktop sidebar inside `display:none` at this width: every box measures 0 × 0 and `display:none` on
an ancestor removes the subtree from the accessibility tree, so a screen reader at 390 px meets the
four links exactly once. axe reports no `landmark-unique` violation in any combination. The only
residual risk is that the identical label is safe *only* because exactly one ever renders — distinct
labels would be cheap insurance at the `md` boundary.

## NOT VERIFIED — stated plainly

1. **No real iPhone.** Everything here is Chromium and WebKit at 390×844 with an iOS user agent.
   Both headless engines report `env(safe-area-inset-bottom) = 0`, so the 15 px tab-bar clearance is
   the no-notch case; the `safe-pb` and `env()` in the CSS look right but need one look on a device.
   The tap-latency numbers are CDP throttling, not a phone on a touchline.
2. **The unthrottled timings come from a wired link in France**, not from a phone at a pitch. That is
   why the throttled runs exist and why they are the ones that matter.
3. **All lanes have reported.** Eight areas were covered: authentication and arrival · calendar and
   availability · trainings and attendance · match hub, sheet and composition · team, roster, profiles
   and invites · statistics · game mode, ratings, recap and retroactive entry · and one cross-cutting
   pass over the whole set. Three things in the live-match lane could not be reached: the
   man-of-the-match note floor (both accounts are gated out of the notes on the only eligible match),
   the **not-yet-open** rating state (the only two future fixtures belonged to other lanes), and a
   reload while still offline, which would not reproduce reliably and is reported as unknown rather
   than guessed. `KICKOFF` latency went unmeasured because the `MutationObserver` was detached by a
   React re-render before the mutation landed.
4. **Within the match hub and composition lane, four things were read rather than run:** a real
   finger drag on a real device (pointer events were synthesised, in both engines); the editor's
   no-JavaScript fallback; whether « Marquer comme terminé » asks for confirmation (it was never
   tapped); and server-side rejection of 8 starters on any path other than the sheet. Native
   date/time rendering (« 10/04/2026, 10:30 AM » under `fr-FR` on `/modifier`) and the
   browser-language validation bubbles are deliberately not filed. The date and time rendering is
   **fixed and in review as #116**, and the answer chosen there is worth knowing because it is the
   right one: rather than build a custom picker, the app **echoes the value under the native control**
   in DD/MM/YYYY and 24h. The validation bubbles are the genuinely irreducible half — a browser string
   in the browser's language, with no API to translate it — so they stay here as a stated limit rather
   than becoming a defect nobody can close.
5. **The last-coach refusal was not exercised.** AS Dimanche has two coaches and manufacturing the
   state would mean demoting one. The path is `wouldLeaveNoCoach` plus the explanatory sentence at
   `joueur/[id]/page.tsx:196-201`, which replaces the role buttons rather than letting them fail —
   read, not run. Note this is the guard that makes D8 reachable.
6. **A genuine cross-team `[id]` could not be tested.** The seed has one team, and `getPlayerProfile`
   scopes by `teamId`, so a foreign membership id is code-identically a 404 and empirically
   indistinguishable from a nonexistent one. Verified by reading the query, not by a second team.
7. **Forged requests were not made.** Server Action guards are read in source and covered by unit
   tests, but "a POST to a closed pointage window is refused" is read, not observed. No UI call site
   offers the control, so there was nothing to tap.
8. **Contrast was not measured with a meter.** This audit relies on axe's zero colour-contrast
   violations. One lane reported two contrast *blockers* which I **rejected and it withdrew**: its
   helper compared text against `oklab(… / 0.15)` as though opaque, rather than compositing 15 % alpha
   over the surface, producing impossible 1.00:1 and 1.02:1 ratios for elements that are plainly
   legible in screenshots. Any contrast claim made that way is void. The two I would still put a meter
   on are the 12 px `text-ink-muted` « Présent »/« Absent » at rest and the `text-ink-subtle` jersey
   numbers.
9. **Four seeded states were observe-only** and nothing was written to them: the FC des Deux-Ponts
   match finished with an empty log, and trainings T2 (19/09) and T3 (26/09). So "what T3 looks like
   once partially pointed" is unknown, as is whether a coach correcting a cancelled session hits
   another wall.
10. **The audit polluted the data it was auditing, and mostly cleaned up.** A test member `AuditG` was
   briefly named in the coach's season statistics; its membership has been **removed through the UI**
   and verified — `/equipe` reads « 13 joueurs » again and the « 1 joueur n'a encore jamais été
   pointé » sentence is gone. Team colours and name were recorded before being changed and restored.
   Trainings created by the audit were deleted and the four seeded sessions verified byte-identical to
   the first read. **Two residues remain for the owner:** the orphaned `users` row for `auditg` (it has
   no team, so it appears in no roster, no stats and no ranking, but clearing it needs a manual
   `DELETE`), and **three matches named « UX Audit H », « UX Audit H retro » and « UX Audit H retro 2 »**
   — `5d187aaf-989e-449f-ac7d-219d6a41f14f`, `94e1dbcb-033d-429e-b4ef-a94190c4770c`,
   `d371fb5c-f2bb-4021-af71-6dc20d7804e5`. These are **legitimately undeletable**: `/modifier` only
   offers « Supprimer » while the event log is empty (decision 003) and `deleteMatch` refuses regardless
   (`lib/match/actions.ts:146`), and all three now carry logs. That is invariant 1 working, not a bug —
   but it means a match played in the app can never be removed, which is worth the owner knowing as a
   property rather than discovering as a surprise. Karim's ratings on CS Morvan were also submitted and
   cannot be withdrawn. The cleanup paid for itself — running
   the removal is what produced the evidence for D29, D32 and D33. « UX Audit D » was created and
   deleted and is verified gone (404, absent from the calendar); Étoile du Parc's sheet was checked row
   by row back to 7 starters / 3 substitutes / 1 supporter / 2 out, both of its compositions were
   restored to the seeded teams, and the extra 90′ plan created to test D42 was deleted. **Several
   defects above — D3, D14, D15, D19, D42 — exist only because writes on dev were authorised.** Each
   of them is invisible to a read-only audit.
11. **The data moved under the auditors mid-run, twice**, because seven browsers shared one preview
   database. One near-miss is worth recording as a method note: `/equipe` appeared to be 69 px taller
   in dark than in light, and I began writing it up as theme drift. Re-measured with both arms in the

   shared database the only defence is to measure both arms together.
